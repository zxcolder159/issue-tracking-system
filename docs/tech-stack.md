# Предложение по стеку технологий

Статус: стек зафиксирован. Бэкенд и БД уже стартованы (скелет в репозитории), фронтенд — Vue 3 + TypeScript.

## Бэкенд — выбран

- **Java 21 + Spring Boot** (Web MVC, Security, Data JPA).
  Почему: зрелая платформа, на которой естественно реализуются все архитектурные задачи курса — DI, слоистая архитектура (controller → service → repository), декларативная безопасность (проверка ролей в контексте пространства), транзакционность смены статуса. Команда знает Java.
- **PostgreSQL**.
  Почему: критична реляционная целостность — issue ссылается на автора, assignee, пространство и статус (внешние ключи); транзакции нужны для атомарной смены статуса с проверкой правил lifecycle; JSONB — задел под настраиваемые поля.
- **Docker Compose** для локального подъёма БД; **Flyway** для миграций схемы (вводим вместе с первыми миграциями).

## Фронтенд — выбран

- **Vue 3 + TypeScript** (Composition API), сборка **Vite**.
  Почему: команда знает Vue; Composition API хорошо типизируется и позволяет вынести логику в композаблы (работа с API, состояние доски).
- **Drag-n-drop доски:** vue-draggable-plus или vuedraggable (обёртки над Sortable.js) — покрывают типовой сценарий kanban-доски; если понадобится более тонкий контроль — Pragmatic Drag and Drop (framework-agnostic, от Atlassian).
- **UI-кит** (date picker, таблицы для List view): Element Plus / Ant Design Vue / Naive UI — конкретный кит определим вместе с прототипом доски.

Рассмотренные альтернативы: React + dnd-kit (меньше опыта у команды) и серверный рендеринг Thymeleaf + HTMX (интерактивную доску с drag-n-drop пришлось бы дописывать руками). Выбор UI-кита подтвердим коротким прототипом доски.

## Служебные и инфраструктурные решения

- **API:** REST + JSON, документация OpenAPI (springdoc).
- **Soft delete:** колонка `deleted_at`; корзина — отдельный режим выдачи удалённых записей, а не глобальный фильтр по таблице (детали видимости корзины уточняем у заказчика, вопрос 16).
- **Тесты:** JUnit 5 + Spring Boot Test + Testcontainers (интеграционные тесты на PostgreSQL); e2e через Playwright после выбора фронта.
- **CI:** GitHub Actions — сборка и тесты на каждый pull request.
- **Качество кода:** Spotless/Checkstyle на бэкенде, ESLint/Prettier на фронтенде.

## Открытые технологические вопросы

- Обновление доски в реальном времени: WebSocket/SSE или обычный polling — зависит от ответа заказчика про совместную работу (вопрос 21).
- Полнотекстовый поиск: на наши масштабы, скорее всего, достаточно PostgreSQL FTS; отдельный движок не закладываем.
- Хранение вложений (если войдут в скоуп): локальная файловая система или S3-совместимое хранилище.
