# Use Cases: Issue Tracking System

## Акторы

- **Гость:** неавторизованный посетитель.
- **Пользователь:** вошёл в систему, но может ещё не состоять ни в одном проекте.
- **Участник проекта:** состоит в проекте с ролью Developer или QA. Ведёт issues, которые создал сам. У QA права как у Developer, поэтому на диаграмме это один актор. Роль задаётся в каждом проекте отдельно: один пользователь может быть Project Lead в одном проекте и Developer в другом.
- **Project Lead:** тоже участник проекта, ему доступно всё, что Участнику проекта, но с любыми issues. Дополнительно управляет участниками и lifecycle.
- **Admin:** администратор всей системы, он один. В любом проекте может всё, что Project Lead, даже не состоя в нём. Дополнительно создаёт и удаляет проекты.

На диаграмме юзкейсов связи от Project Lead и Admin идут только к их собственным юзкейсам, общие юзкейсы участника не дублируются.

## Полный список юзкейсов

### Регистрация и вход

- Гость: зарегистрироваться в системе (UC-1).
- Гость: войти в систему (UC-2).
- Гость: восстановить забытый пароль (UC-3).
- Пользователь: выйти из системы (UC-4).

### Проекты и участники

- Admin: создать проект и назначить в нём Project Lead (UC-5).
- Admin: удалить проект (UC-6).
- Project Lead: изменить название и описание проекта (UC-7).
- Project Lead: добавить пользователя в проект и выбрать ему роль (UC-8).
- Project Lead: изменить роль участника (UC-9).
- Project Lead: исключить участника из проекта (UC-10).
- Участник проекта: перейти в другой проект, в котором он состоит (UC-11).
- Участник проекта: посмотреть состав участников и их роли (UC-12).

### Настройка lifecycle

- Участник проекта: посмотреть статусы и переходы между ними (UC-13).
- Project Lead: создать статус и связать его с другими статусами. (UC-14).
- Project Lead: переименовать статус (UC-15).
- Project Lead: изменить порядок столбцов на доске (UC-16).
- Project Lead: добавить переход между двумя статусами и выбрать роли, которым он разрешён. (UC-17).
- Project Lead: изменить роли, которым разрешён переход (UC-18).
- Project Lead: удалить переход (UC-19).
- Project Lead: удалить статус и перенести его issues в другой статус (UC-20).

### Просмотр

- Участник проекта: посмотреть доску проекта (Board view) (UC-21).
- Участник проекта: найти и отфильтровать issues на доске (например, по assignee) (UC-22).
- Участник проекта: посмотреть полный список issues (List view) (UC-23).
- Участник проекта: открыть карточку issue и посмотреть все поля (UC-24).
- Участник проекта: посмотреть диаграмму Ганта (UC-25).

### Работа с issues

- Участник проекта: создать issue (UC-26).
- Developer, QA: отредактировать свою issue: текст с ограниченным Markdown (жирный, курсив, ссылки), assignee, даты начала и окончания в календаре (date picker), статус (UC-27).
- Project Lead: отредактировать любую issue и назначить на неё любого пользователя (UC-27).
- Developer, QA: выбрать несколько своих issues в List view и изменить их поля или переместить в корзину (UC-28, UC-30).
- Project Lead: выбрать любые issues в List view и изменить их поля или переместить в корзину (UC-28, UC-30).

### Смена статуса

- Developer, QA: перенести карточку своей issue в другой столбец по правилам перехода (UC-29).
- Project Lead: перенести карточку любой issue (UC-29).

### Удаление и корзина

- Developer, QA: переместить свою issue в корзину (UC-30).
- Project Lead: переместить в корзину любую issue или несколько сразу (UC-30).
- Участник проекта: посмотреть корзину (UC-31).
- Участник проекта: восстановить issue из корзины (UC-32).

## Что делает система

Это не юзкейсы: правила, которые система выполняет сама, без действий пользователя.

- Новый статус появляется последней колонкой на доске.
- Переход между статусами работает в обе стороны.
- Новая issue попадает в первый статус lifecycle.
- В List у Developer и QA чекбоксы есть только у issues, которые они создали сами. В корзине им видны только такие issues.
- Если удалить первый статус, новые issues попадают в следующий.
- Issue лежит в корзине 7 дней, потом система удаляет её окончательно.

## Подробное описание юзкейсов

UC-20, UC-29 и UC-32 расписаны по полному шаблону, остальные по обязательным полям. Названия кнопок и разделов взяты из макетов `docs/ui/ui.drawio`.

Для UC-1, 2, 14, 20, 26, 27, 28, 29, 30 и 32 нарисованы диаграммы активностей (`docs/uml/uc-*.png`). Синим на них отмечены действия пользователя, серым действия системы. Ромбы покрашены так же: синий означает выбор пользователя, серый проверку, которую делает система.

Расширение записано как ссылка на другой юзкейс: номер шага, на котором можно перейти, условие перехода и сам юзкейс. Например, «1a. Гость не помнит пароль: UC-3» значит, что на шаге 1 юзкейса UC-2 гость может перейти к восстановлению пароля. На диаграмме юзкейсов каждому расширению соответствует стрелка «extend». Отклонения, которые не ведут в другой юзкейс (ошибка, отмена, нет прав), записаны в «Альтернативных сценариях».

### Регистрация и вход

#### UC-1

**Название:** Регистрация.

**Акторы:** Гость.

**Цели:** получить аккаунт, чтобы присоединиться к работе над проектами.

**Основной сценарий успеха:**
1. Гость открывает страницу входа и выбирает «Sign up».
2. Вводит имя, почту и пароль.
3. Система проверяет, что почта ещё не занята, и создаёт аккаунт.
4. Гость входит в систему как Пользователь. Пока его не добавили ни в один проект, список проектов пуст.

**Альтернативные сценарии:**
- 3a. Почта уже занята: система сообщает об этом, гость вводит другую почту.

#### UC-2

**Название:** Вход в систему.

**Акторы:** Гость.

**Цели:** начать работу под своим аккаунтом.

**Расширения:**
- 1a. Гость не помнит пароль: UC-3 «Восстановление пароля».

**Основной сценарий успеха:**
1. Гость вводит почту и пароль на странице входа.
2. Система проверяет учётные данные.
3. Система открывает доску последнего проекта, с которым работал пользователь.

**Альтернативные сценарии:**
- 2a. Почта или пароль неверные: система сообщает об ошибке, гость вводит данные заново.
- 3a. Пользователь пока не состоит ни в одном проекте: система показывает пустой список проектов.

#### UC-3

**Название:** Восстановление пароля.

**Акторы:** Гость.

**Цели:** вернуть доступ к аккаунту, если пароль забыт.

**Основной сценарий успеха:**
1. На странице входа гость выбирает «Forgot password?».
2. Вводит почту, указанную при регистрации.
3. Система отправляет на эту почту письмо со ссылкой для сброса пароля.
4. Гость переходит по ссылке и задаёт новый пароль.
5. Система сохраняет пароль, после этого гость может войти (UC-2).

#### UC-4

**Название:** Выход из системы.

**Акторы:** Пользователь.

**Цели:** завершить сеанс, чтобы никто не работал под его аккаунтом.

**Основной сценарий успеха:**
1. Пользователь открывает меню со своим именем в шапке.
2. Выбирает «Log out».
3. Система завершает сеанс и открывает страницу входа.

### Проекты и участники

#### UC-5

**Название:** Создание проекта.

**Акторы:** Admin.

**Цели:** завести проект для новой команды и назначить ответственного за него.

**Основной сценарий успеха:**
1. Admin выбирает «Create project» в переключателе проектов в шапке.
2. Вводит название и описание проекта.
3. Выбирает пользователя, который станет Project Lead.
4. Система создаёт проект со статусами по умолчанию (To Do, In Progress, In Review, Done) и добавляет выбранного пользователя с ролью Project Lead.

#### UC-6

**Название:** Удаление проекта.

**Акторы:** Admin.

**Цели:** убрать проект, который больше не нужен.

**Основной сценарий успеха:**
1. Admin открывает «Settings», раздел «General». Блок «Delete project» виден только ему.
2. Нажимает «Delete project».
3. Система просит подтвердить удаление.
4. Admin подтверждает.
5. Система удаляет проект вместе с его issues, участники теряют к нему доступ.

#### UC-7

**Название:** Изменение названия и описания проекта.

**Акторы:** Project Lead.

**Цели:** держать название и описание проекта актуальными.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «General».
2. Меняет «Name» и «Description».
3. Нажимает «Save».
4. Система сохраняет изменения, новое название видно в шапке у всех участников.

#### UC-8

**Название:** Добавление участника в проект.

**Акторы:** Project Lead.

**Цели:** дать коллеге доступ к проекту с нужными правами.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «Members».
2. В поле «User name or email» находит пользователя.
3. Выбирает ему роль: Developer, QA или Project Lead.
4. Нажимает «Add».
5. Система добавляет пользователя в таблицу участников. Проект сразу появляется у него в переключателе проектов.

#### UC-9

**Название:** Изменение роли участника.

**Акторы:** Project Lead.

**Цели:** поменять права участника, когда меняются его обязанности.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «Members».
2. В строке участника выбирает новую роль в столбце «Role».
3. Система сохраняет роль, новые права действуют сразу.

#### UC-10

**Название:** Исключение участника из проекта.

**Акторы:** Project Lead.

**Цели:** закрыть доступ к проекту человеку, который в нём больше не работает.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «Members».
2. Нажимает «Remove» в строке участника.
3. Система просит подтвердить.
4. Project Lead подтверждает.
5. Система убирает участника из проекта. Issues, которые он создал или на которые назначен, остаются в проекте.

#### UC-11

**Название:** Переход в другой проект.

**Акторы:** Участник проекта.

**Цели:** переключиться на работу в другом своём проекте.

**Основной сценарий успеха:**
1. Пользователь открывает переключатель «Project» в шапке.
2. Система показывает проекты, в которых он состоит.
3. Пользователь выбирает проект.
4. Система открывает доску выбранного проекта. Права определяются ролью пользователя в этом проекте.

#### UC-12

**Название:** Просмотр участников проекта.

**Акторы:** Участник проекта.

**Цели:** узнать, кто работает в проекте и с какими ролями.

**Основной сценарий успеха:**
1. Пользователь открывает «Settings», раздел «Members».
2. Система показывает таблицу участников с почтой и ролью. Менять роли и состав может только Project Lead, у остальных таблица только для чтения.

### Настройка lifecycle

#### UC-13

**Название:** Просмотр статусов и переходов.

**Акторы:** Участник проекта.

**Цели:** узнать, какие переходы между статусами есть в проекте и каким ролям они разрешены.

**Основной сценарий успеха:**
1. Пользователь открывает «Settings», раздел «Lifecycle graph».
2. Система показывает статусы в порядке колонок на доске и таблицу переходов с ролями. Менять их может только Project Lead, у остальных страница только для чтения.

#### UC-14

**Название:** Создание статуса.

**Акторы:** Project Lead.

**Цели:** добавить в процесс новый этап работы.

**Основной сценарий успеха:**
1. Project Lead нажимает «+ Add status» в конце доски.
2. В окне «Add status» вводит название.
3. В «Connect to» отмечает статусы, с которыми будет связан новый.
4. В «Roles» выбирает роли, которым разрешены эти переходы.
5. Нажимает «Add».
6. Система создаёт статус и переходы, новая колонка появляется в конце доски.

Другой способ: ввести название в поле «New status name» на странице «Lifecycle graph» и нажать «+ Add». Тогда статус создаётся без переходов, и их нужно добавить отдельно (UC-17).

#### UC-15

**Название:** Переименование статуса.

**Акторы:** Project Lead.

**Цели:** исправить или уточнить название этапа.

**Основной сценарий успеха:**
1. Project Lead открывает меню «⋯» в заголовке колонки и выбирает «Rename». Другой способ: исправить название в поле на странице «Lifecycle graph».
2. Вводит новое название и подтверждает.
3. Система сохраняет название. Issues остаются в этом статусе, меняется только подпись колонки.

#### UC-16

**Название:** Изменение порядка столбцов.

**Акторы:** Project Lead.

**Цели:** расположить колонки в том порядке, в котором идёт работа.

**Основной сценарий успеха:**
1. Project Lead перетаскивает заголовок колонки на доске на новое место. Другой способ: перетащить строку статуса за «⋮⋮» на странице «Lifecycle graph».
2. Система сохраняет порядок, у всех участников колонки идут в новом порядке. Если первым стал другой статус, новые issues теперь попадают в него.

#### UC-17

**Название:** Добавление перехода между статусами.

**Акторы:** Project Lead.

**Цели:** разрешить переносить issues между двумя статусами.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «Lifecycle graph».
2. В строке над таблицей переходов выбирает два статуса.
3. В «Roles» выбирает роли, которым разрешён переход.
4. Нажимает «+ Add».
5. Система добавляет переход в таблицу. Переход работает в обе стороны, на доске эти колонки становятся доступны для выбранных ролей.

#### UC-18

**Название:** Изменение ролей перехода.

**Акторы:** Project Lead.

**Цели:** поменять, кто может переносить issues между двумя статусами.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «Lifecycle graph».
2. В строке перехода меняет список ролей в «Allowed roles».
3. Нажимает «Save».
4. Система сохраняет изменения. Переносить issues между этими статусами теперь могут только выбранные роли.

#### UC-19

**Название:** Удаление перехода.

**Акторы:** Project Lead.

**Цели:** запретить переносить issues между двумя статусами.

**Основной сценарий успеха:**
1. Project Lead открывает «Settings», раздел «Lifecycle graph».
2. Нажимает «Delete» в строке перехода.
3. Система удаляет переход. Issues, которые уже лежат в этих статусах, остаются на месте.

#### UC-20

**Название:** Удаление статуса из lifecycle.

**Акторы:** Project Lead.

**Цели:** удалить статус, которым команда больше не пользуется, вместе с его столбцом на доске.

**Условие запуска:** статус больше не нужен команде.

**Предусловия / контекст:** пользователь вошёл, у него роль Project Lead, статус есть в lifecycle. Статус с issues удалить можно, если выбрать, куда их перенести.

**Основной сценарий успеха:**
1. Пользователь выбирает «Delete status» в меню столбца на доске или «Delete» на странице «Lifecycle graph».
2. Система проверяет ограничения и показывает, сколько issues в статусе.
3. Пользователь выбирает статус для переноса issues и подтверждает удаление.
4. Система переносит issues и удаляет статус вместе со столбцом и переходами.
5. Доска и граф lifecycle обновляются.

**Альтернативные сценарии:**
- 2a. Статус единственный: удаление запрещено, система объясняет почему.
- 2b. После удаления часть статусов окажется не связана с остальными: система предупреждает, пользователь подтверждает удаление или отменяет его.
- 2c. В статусе нет issues: выбор статуса для переноса пропускается.
- Если статус нужен, но называется неудачно, его можно переименовать (UC-15) вместо удаления.

### Просмотр

#### UC-21

**Название:** Просмотр доски.

**Акторы:** Участник проекта.

**Цели:** видеть, на каком этапе находятся issues проекта.

**Расширения:**
- 2a. Пользователю нужны не все issues, а только некоторые: UC-22 «Поиск и фильтрация issues».
- 3a. Пользователь хочет перевести issue в другой статус: UC-29 «Смена статуса issue на доске».

**Основной сценарий успеха:**
1. Пользователь открывает проект или вкладку «Board».
2. Система показывает колонки в порядке статусов, в заголовке колонки число issues.
3. На карточке видны название issue и assignee. Изменения других участников появляются сразу, без перезагрузки страницы.

#### UC-22

**Название:** Поиск и фильтрация issues.

**Акторы:** Участник проекта.

**Цели:** быстро найти нужные issues среди всех задач проекта.

**Основной сценарий успеха:**
1. Пользователь выбирает значения в фильтрах «Assignee», «Priority» или «Type».
2. При необходимости вводит часть названия в «Search by name...».
3. Система оставляет только подходящие issues.
4. При переключении на «List» или «Gantt» фильтры сохраняются.

#### UC-23

**Название:** Просмотр списка issues.

**Акторы:** Участник проекта.

**Цели:** увидеть все issues проекта с основными полями в одной таблице.

**Расширения:**
- 2a. Пользователь хочет изменить сразу несколько issues: UC-28 «Массовое изменение issues».

**Основной сценарий успеха:**
1. Пользователь открывает вкладку «List».
2. Система показывает таблицу со столбцами Name, Status, Assignee, Priority, Type, Start, Due.
3. По клику на строку открывается issue (UC-24).

#### UC-24

**Название:** Просмотр issue.

**Акторы:** Участник проекта.

**Цели:** увидеть все поля issue.

**Расширения:**
- 3a. Пользователь вправе редактировать issue и хочет изменить её поля: UC-27 «Редактирование issue».

**Основной сценарий успеха:**
1. Пользователь нажимает на карточку на доске или на строку в списке.
2. Система открывает окно issue поверх текущего экрана: название, описание и все поля.
3. Если у пользователя нет прав на редактирование этой issue, поля только для чтения.
4. Пользователь закрывает окно кнопкой «✕».

#### UC-25

**Название:** Просмотр диаграммы Ганта.

**Акторы:** Участник проекта.

**Цели:** увидеть сроки issues на шкале времени и заметить пересечения и просрочки.

**Основной сценарий успеха:**
1. Пользователь открывает вкладку «Gantt».
2. Система показывает слева названия issues, справа полосы от даты начала до даты окончания. Линия «Today» отмечает текущую дату.
3. По клику на название открывается issue (UC-24).

### Работа с issues

#### UC-26

**Название:** Создание issue.

**Акторы:** Участник проекта.

**Цели:** зафиксировать новую задачу в проекте.

**Основной сценарий успеха:**
1. Пользователь нажимает «+ Create issue».
2. Система открывает пустое окно issue.
3. Пользователь вводит название и заполняет обязательные поля: Type, Priority, Start date, Due date. Description и Assignee можно оставить пустыми.
4. Нажимает «Save».
5. Система создаёт issue в первом статусе lifecycle, карточка появляется в первой колонке доски. Пользователь записывается как автор issue.

**Альтернативные сценарии:**
- 4a. Не заполнено обязательное поле: система подсвечивает его и не создаёт issue, пользователь дозаполняет поля.

#### UC-27

**Название:** Редактирование issue.

**Акторы:** Developer или QA (только свои issues), Project Lead (любые issues, может назначить любого пользователя).

**Цели:** держать issue в актуальном состоянии: содержимое, исполнителя, сроки и статус.

**Основной сценарий успеха:**
1. В открытом окне issue пользователь меняет нужные поля: название, описание, Type, Priority, Assignee, Start date, Due date, Status. В описании можно выделить текст жирным или курсивом и добавить ссылку кнопками «B», «I», «Link». Даты выбираются в календаре. В «Status» можно выбрать только статус, переход в который разрешён роли пользователя.
2. Нажимает «Save».
3. Система проверяет, что дата окончания не раньше даты начала.
4. Система сохраняет изменения, другие участники сразу их видят: имя исполнителя появляется на карточке, полоса на диаграмме Ганта обновляется, при смене статуса карточка переезжает в нужную колонку.

**Альтернативные сценарии:**
- 3a. Дата окончания раньше даты начала: система подсвечивает поля дат и ничего не сохраняет, пользователь выбирает даты заново.

#### UC-28

**Название:** Массовое изменение issues.

**Акторы:** Developer или QA (только свои issues), Project Lead (любые issues).

**Цели:** изменить сразу несколько issues, не открывая каждую.

**Основной сценарий успеха:**
1. Пользователь открывает вкладку «List».
2. Отмечает нужные issues чекбоксами. Чекбоксы есть только у issues, которые пользователь вправе редактировать.
3. На панели над таблицей нажимает «Edit...».
4. Система открывает окно «Edit issues». Если поле у всех выбранных issues одинаковое, в нём показано это значение, если разное, то «Mixed values».
5. Пользователь меняет нужные поля и нажимает «Apply».
6. Система применяет изменения ко всем выбранным issues, поля, которые не трогали, остаются как были.

**Альтернативные сценарии:**
- 6a. Смену статуса нельзя применить к части issues по правилам переходов: эти issues система не меняет совсем, остальные меняет и сообщает, сколько issues не изменилось.

### Смена статуса

#### UC-29

**Название:** Смена статуса issue на доске.

**Акторы:** Developer или QA (только свои issues), Project Lead (любые issues).

**Цели:** перевести issue в другой разрешённый статус.

**Условие запуска:** состояние работы над issue изменилось, и участник хочет отразить это на доске.

**Предусловия / контекст:** пользователь вошёл и состоит в проекте, issue на доске в статусе S, lifecycle настроен.

**Основной сценарий успеха:**
1. Пользователь выбирает карточку issue на доске.
2. Система подсвечивает столбцы, в которые роли пользователя разрешён переход из S. Остальные столбцы недоступны.
3. Пользователь переносит карточку в столбец T.
4. Система сохраняет новый статус, карточка остаётся в столбце T. Другие участники сразу видят изменение на своей доске.

**Альтернативные сценарии:**
- 1a. Нет прав на изменение issue (Developer и issue, созданная другим пользователем): карточку нельзя взять, подсказка при наведении объясняет почему.
- 3a. Карточку отпустили над недоступным столбцом: карточка возвращается на место, статус не меняется.
- Сменить статус можно и в окне issue (UC-27), а у нескольких issues сразу в «List» (UC-28).

### Удаление и корзина

#### UC-30

**Название:** Перемещение issue в корзину.

**Акторы:** Developer или QA (только свои issues), Project Lead (любые issues).

**Цели:** убрать ненужную issue с доски так, чтобы её можно было вернуть.

**Основной сценарий успеха:**
1. Пользователь нажимает «Move to trash» в окне issue. Чтобы удалить несколько issues сразу, он отмечает их в «List» и нажимает «Move to trash» на панели над таблицей.
2. Система просит подтвердить.
3. Пользователь подтверждает.
4. Система убирает issues с доски и из списка и кладёт их в корзину на 7 дней.

**Альтернативные сценарии:**
- 3a. Пользователь отменяет удаление: issues остаются на месте.

#### UC-31

**Название:** Просмотр корзины.

**Акторы:** Участник проекта.

**Цели:** увидеть удалённые issues и сколько дней им осталось храниться.

**Расширения:**
- 3a. Пользователь хочет вернуть issue из корзины: UC-32 «Восстановление issue из корзины».

**Основной сценарий успеха:**
1. Пользователь нажимает «Trash» в шапке.
2. Система показывает таблицу со столбцами Name, Status, Moved to trash, Days left. Developer и QA видят только issues, которые создали сами, Project Lead видит все.
3. Пользователь может найти issue по названию через «Search by name...».

#### UC-32

**Название:** Восстановление issue из корзины.

**Акторы:** Developer или QA (только свои issues), Project Lead (любые issues).

**Цели:** отменить ошибочное удаление issue без потери данных.

**Условие запуска:** issue удалили по ошибке, и пользователь хочет вернуть issue в работу.

**Предусловия / контекст:** пользователь вошёл, issue лежит в корзине.

**Основной сценарий успеха:**
1. Пользователь открывает корзину проекта.
2. Находит issue по названию.
3. Нажимает «Restore».
4. Issue возвращается на доску в исходный статус со всеми полями и пропадает из корзины.

**Альтернативные сценарии:**
- 2a. Поиск ничего не находит (прошло больше 7 дней, и система удалила issue окончательно): восстановить issue нельзя, сценарий завершается.
- 4a. Исходного статуса больше нет в lifecycle: система просит выбрать статус для восстановления.
