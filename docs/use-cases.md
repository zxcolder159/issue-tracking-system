# Use Cases: Issue Tracking System

## Акторы

- **Гость:** неавторизованный посетитель.
- **Пользователь:** вошёл в систему, но может ещё не состоять ни в одном проекте.
- **Участник проекта** (абстрактный, наследуется от Пользователя): состоит в проекте. Сам по себе не встречается, у каждого участника есть одна из ролей ниже, и каждая роль наследует все юзкейсы Участника проекта. Роль задаётся в каждом проекте отдельно: один пользователь может быть Project Lead в одном проекте и Developer в другом.
  - **Developer:** ведёт issues, которые создал сам.
  - **QA:** права как у Developer (допущение, заказчик права QA не оговорил).
  - **Project Lead:** управляет всеми issues проекта, участниками и lifecycle.
- **Admin** (наследуется от Project Lead): администратор всей системы, он один. В любом проекте может всё, что Project Lead, даже не состоя в нём. Дополнительно создаёт и удаляет проекты.
- **Планировщик:** системный актор (время), очищает корзину.

## Полный список юзкейсов

### Регистрация и вход

- Гость: зарегистрироваться в системе.
- Гость: войти в систему.
- Гость: восстановить забытый пароль.
- Пользователь: выйти из системы.

### Проекты и участники

- Admin: создать проект и назначить в нём Project Lead.
- Admin: удалить проект.
- Project Lead: изменить название и описание проекта.
- Project Lead: пригласить пользователя в проект.
- Project Lead: изменить роль участника.
- Project Lead: исключить участника из проекта.
- Пользователь: принять или отклонить приглашение в проект.
- Участник проекта: посмотреть состав участников и их роли.
- Участник проекта: покинуть проект.

### Настройка lifecycle

- Участник проекта: посмотреть граф lifecycle (статусы и переходы).
- Project Lead: создать статус вместе со столбцом доски.
- Project Lead: переименовать статус.
- Project Lead: изменить порядок столбцов на доске.
- Project Lead: разрешить переход между статусами.
- Project Lead: запретить переход между статусами.
- Project Lead: удалить статус и перенести его issues в другой статус.

### Просмотр

- Участник проекта: посмотреть доску проекта (Board view).
- Участник проекта: найти и отфильтровать issues на доске (например, по assignee).
- Участник проекта: посмотреть полный список issues (List view).
- Участник проекта: открыть карточку issue и посмотреть все поля.
- Участник проекта: посмотреть диаграмму Ганта.

### Работа с issues

- Участник проекта: создать issue.
- Developer, QA: отредактировать свою issue (текст с ограниченным Markdown: жирный, курсив, ссылки).
- Developer, QA: назначить assignee на свою issue.
- Developer, QA: задать даты начала и окончания своей issue в календаре (date picker).
- Project Lead: отредактировать любую issue.
- Project Lead: назначить assignee на любую issue, выбрав любого пользователя.
- Project Lead: задать даты начала и окончания любой issue.
- Project Lead: выполнить массовую операцию над несколькими issues в List view.

### Смена статуса

- Developer, QA: перенести карточку своей issue в другой столбец по правилам перехода.
- Developer, QA: сменить статус своей issue в открытой карточке.
- Project Lead: сменить статус любой issue любым из этих двух способов.

### Удаление и корзина

- Developer, QA: переместить свою issue в корзину.
- Project Lead: переместить в корзину любую issue или несколько сразу.
- Участник проекта: посмотреть корзину (Developer и QA видят только свои issues).
- Участник проекта: восстановить issue из корзины.
- Планировщик: окончательно удалить issues, которые лежат в корзине больше 7 дней.

## Подробное описание трёх юзкейсов

### UC-1

**Название:** Смена статуса issue на доске.

**Акторы:** Developer или QA (только свои issues), Project Lead (любые issues).

**Цели:** перевести issue в другой разрешённый статус.

**Условие запуска:** состояние работы над issue изменилось, и участник хочет отразить это на доске.

**Предусловия / контекст:** пользователь вошёл и состоит в проекте, issue на доске в статусе S, lifecycle настроен.

**Расширения:**
- 1a. Нет прав на изменение issue (Developer и issue, созданная другим пользователем): карточку нельзя взять, подсказка при наведении объясняет почему.
- 3a. Карточку отпустили над недоступным столбцом: карточка возвращается на место, статус не меняется.
- 4a. Пока карточку переносили, другой пользователь изменил статус issue или правила lifecycle: изменение не применяется, система предлагает обновить доску.
- 4b. Сессия истекла: система просит войти заново, изменение не применяется.

**Основной сценарий успеха:**
1. Пользователь выбирает карточку issue на доске.
2. Система подсвечивает столбцы, в которые разрешён переход из S. Остальные столбцы недоступны.
3. Пользователь переносит карточку в столбец T.
4. Система проверяет, что переход S → T всё ещё разрешён.
5. Система сохраняет новый статус, карточка остаётся в столбце T. Другие участники сразу видят изменение на своей доске.

**Альтернативные сценарии:** смена статуса через список в карточке issue, массовая смена статуса в List view.

### UC-2

**Название:** Удаление статуса из lifecycle.

**Акторы:** Project Lead.

**Цели:** удалить статус, которым команда больше не пользуется, вместе с его столбцом на доске.

**Условие запуска:** статус больше не нужен команде.

**Предусловия / контекст:** пользователь вошёл, у него роль Project Lead, статус есть в lifecycle. Допущение (вопрос 9): статус с issues удалить можно, если выбрать, куда их перенести.

**Расширения:**
- 2a. Статус единственный, начальный или конечный: удаление запрещено, система объясняет почему.
- 2b. После удаления пропадёт путь от начального статуса к конечному: система предупреждает и просит подтвердить или отменить.
- 2c. В статусе нет issues: выбор статуса для переноса пропускается.

**Основной сценарий успеха:**
1. Пользователь открывает настройки lifecycle и выбирает «Удалить статус».
2. Система проверяет ограничения и показывает, сколько issues в статусе.
3. Пользователь выбирает статус для переноса issues и подтверждает удаление.
4. Система переносит issues и удаляет статус вместе со столбцом и переходами.
5. Доска и граф lifecycle обновляются.

**Альтернативные сценарии:** скрыть или переименовать статус вместо удаления.

### UC-3

**Название:** Восстановление issue из корзины.

**Акторы:** участник проекта (любая роль). Допущение (вопрос 12): Project Lead видит в корзине все issues, Developer и QA только созданные ими.

**Цели:** отменить ошибочное удаление issue без потери данных.

**Условие запуска:** issue удалили по ошибке, и пользователь хочет вернуть issue в работу.

**Предусловия / контекст:** пользователь вошёл и имеет доступ к корзине, issue переместили в корзину. В корзине пользователь видит только те issues, которые может восстановить.

**Расширения:**
- 2a. Поиск ничего не находит (прошло больше 7 дней, и планировщик очистил корзину): восстановить issue нельзя, сценарий завершается.
- 4a. Срок хранения истёк, пока пользователь был в корзине: восстановление невозможно, issue пропадает из списка.
- 5a. Исходного статуса больше нет в lifecycle: система просит выбрать статус для восстановления.

**Основной сценарий успеха:**
1. Пользователь открывает корзину проекта.
2. Находит issue по названию.
3. Нажимает «Восстановить».
4. Система проверяет срок хранения.
5. Issue возвращается на доску в исходный статус со всеми полями и связями и пропадает из корзины.

**Альтернативные сценарии:** массовое восстановление нескольких issues.
