# Use Cases — Issue Tracking System

Список охватывает весь продукт: ядро Stage 1 и ближайшее развитие (разделы «Развитие» в project-vision). Права ролей QA и Admin окончательно не зафиксированы — см. вопросы к заказчику; там, где сценарий зависит от ответа, сделано разумное допущение, оно отмечено в тексте.

## Акторы

- Гость — неавторизованный посетитель системы.
- Участник пространства (абстрактный) — любой авторизованный пользователь, входящий в пространство; от него наследуются роли Developer, QA, Project Lead и Admin.
- Планировщик — системный актор (время): запускает автоматическую очистку корзины.
- Внешняя система — потребитель REST API (после Stage 1).

## Полный список юзкейсов

### Регистрация и вход

1. Зарегистрироваться в системе, создав аккаунт.
2. Войти в систему под своими учётными данными.
3. Выйти из системы.
4. Восстановить забытый пароль.

### Пространства и участники

5. Создать новое пространство (проект).
6. Добавить участника в пространство по приглашению.
7. Изменить роль участника пространства.
8. Исключить участника из пространства.
9. Покинуть пространство по собственной инициативе.
10. Просмотреть состав участников пространства и их роли.

### Настройка lifecycle

11. Создать статус и связанный с ним столбец доски.
12. Переименовать или отредактировать статус.
13. Изменить порядок столбцов на доске.
14. Задать разрешённый переход между статусами (правило перехода).
15. Удалить или запретить переход между статусами.
16. Удалить статус из lifecycle (с учётом issues, находящихся в нём).
17. Просмотреть граф lifecycle пространства (статусы и переходы).

### Работа с issues

18. Создать issue, заполнив обязательные поля.
19. Просмотреть детали issue в карточке.
20. Отредактировать содержимое issue в рамках полномочий своей роли.
21. Назначить assignee на issue.
22. Сменить автора issue или создать issue от имени другого пользователя (Project Lead).
23. Изменить type или priority issue.
24. Установить или изменить дату (дедлайн) прямо на карточке.
25. Просмотреть доску пространства (Board view).
26. Просмотреть весь бэклог в виде списка (List view).
27. Выполнить массовую операцию над несколькими issues в List view.

### Смена статуса

28. Переместить issue на доске в другой столбец (смена статуса по правилам перехода).

### Удаление и корзина

29. Удалить issue в корзину (soft delete).
30. Массово удалить несколько issues в корзину.
31. Просмотреть корзину пространства.
32. Восстановить issue из корзины.
33. Окончательно удалить issue из корзины до истечения срока хранения.
34. Планировщик автоматически очищает корзину по истечении 7 дней.

### Развитие (после Stage 1)

35. Найти issues по ключевым словам (полнотекстовый поиск).
36. Отфильтровать issues по автору, статусу, приоритету и датам.
37. Добавить комментарий к issue.
38. Просмотреть историю изменений issue.
39. Просмотреть метрики пространства (узкие места lifecycle, просрочки).
40. Внешней системе получить или изменить данные через REST API.

### UC-28. Сменить статус issue перетаскиванием карточки (drag-n-drop)

**Название.** Смена статуса issue через перетаскивание карточки в другой столбец доски.

**Акторы.** Участник пространства (Developer, QA или Project Lead).

**Цели.** Отразить реальный прогресс работы: перевести задачу в следующий статус рабочего процесса.

**Условие запуска.** Пользователь отпустил перетаскиваемую карточку над другим столбцом доски.

**Предусловия / контекст.** Пользователь аутентифицирован и является участником пространства. Issue отображается на доске в статусе S. В пространстве настроен lifecycle: набор статусов и разрешённых переходов между ними.

**Расширения.**
- 4a. Переход S → T не разрешён правилами lifecycle — система возвращает карточку в исходный столбец и объясняет, почему переход запрещён.
- 4b. Роль пользователя не даёт права менять этот issue (например, Developer пытается переместить чужую задачу) — отказ с объяснением полномочий.
- 4c. Статус issue уже изменён другим пользователем параллельно — система не применяет изменение и предлагает обновить доску.
- 3a. Сеанс пользователя истёк — запрос повторной аутентификации, изменение не применяется.

**Основной сценарий успеха.**
1. Пользователь берёт карточку issue и начинает перетаскивание.
2. Доска подсвечивает столбцы, в которые переход из статуса S разрешён правилами.
3. Пользователь отпускает карточку над целевым столбцом T.
4. Система в транзакции проверяет наличие перехода S → T в lifecycle и права пользователя на эту операцию.
5. Система сохраняет новый статус issue.
6. Карточка остаётся в столбце T; изменение сразу видно всем, кто смотрит доску.

**Альтернативные сценарии.** Смена статуса не перетаскиванием, а выбором из списка статусов в карточке issue. Массовая смена статуса для нескольких issues в List view.

### UC-16. Удалить статус из lifecycle пространства

**Название.** Удаление статуса (столбца доски) из жизненного цикла пространства.

**Акторы.** Project Lead или Admin пространства.

**Цели.** Упростить рабочий процесс, убрав ставший лишним статус.

**Условие запуска.** Руководитель проекта решает, что статус больше не нужен, и выбирает «Удалить статус» в настройках lifecycle.

**Предусловия / контекст.** Пользователь аутентифицирован и имеет роль Project Lead или Admin в пространстве. Статус существует в lifecycle. Допущение (вопрос 9 к заказчику не закрыт): удаление статуса с задачами разрешено, но требует явного выбора целевого статуса для переноса.

**Расширения.**
- 2a. В статусе находятся issues — система требует выбрать статус, в который они будут перенесены, и показывает их количество.
- 3a. Статус — единственный в пространстве, начальный или конечный — удаление запрещено с объяснением.
- 3b. После удаления не остаётся пути между начальным и конечным статусами (граф разрывается) — система предупреждает и требует подтвердить или отменить действие.
- 4a. У пользователя нет прав на настройку lifecycle — отказ с объяснением полномочий.

**Основной сценарий успеха.**
1. Project Lead открывает настройки lifecycle и выбирает статус для удаления.
2. Система проверяет ограничения (не единственный, не начальный/конечный) и наличие issues в статусе.
3. При наличии issues пользователь выбирает целевой статус переноса и подтверждает действие.
4. Система в транзакции переносит issues в выбранный статус, удаляет статус вместе со столбцом и всеми входящими и исходящими переходами, пересчитывает порядок столбцов.
5. Доска и граф lifecycle отображаются без удалённого статуса.

**Альтернативные сценарии.** Вместо удаления — скрыть или переименовать статус, сохранив историю. Перенос issues в разные статусы по условию (например, по типу issue).

### UC-32. Восстановить issue из корзины

**Название.** Восстановление удалённой issue из корзины пространства.

**Акторы.** Автор issue, Project Lead или Admin. Допущение (вопрос 12 к заказчику не закрыт): корзина видна этим трём ролям.

**Цели.** Вернуть случайно или ошибочно удалённую задачу в работу без потери данных.

**Условие запуска.** Пользователь обнаружил, что нужная issue удалена, и открыл корзину.

**Предусловия / контекст.** Пользователь аутентифицирован и имеет право просмотра корзины пространства. Issue была удалена (soft delete) менее 7 дней назад и всё ещё находится в корзине.

**Расширения.**
- 4a. С момента удаления прошло 7 дней и планировщик уже окончательно удалил issue — восстановление невозможно, система сообщает об этом.
- 4b. Исходный статус issue был удалён из lifecycle за время нахождения задачи в корзине — система предлагает выбрать статус для восстановления.
- 4c. У пользователя нет права восстанавливать issues — отказ с объяснением полномочий.
- 5a. Правила пространства изменились и исходный статус больше не доступен для issues этого типа — восстановление в ближайший допустимый статус по выбору пользователя.

**Основной сценарий успеха.**
1. Пользователь открывает корзину пространства.
2. Находит нужную issue по названию или идентификатору.
3. Нажимает «Восстановить».
4. Система проверяет срок хранения (менее 7 дней) и права пользователя.
5. Система снимает признак удаления; issue возвращается на доску в исходный статус с сохранением всех полей и связей.
6. Issue исчезает из корзины и снова доступна для работы.

**Альтернативные сценарии.** Массовое восстановление нескольких issues. Окончательное удаление issue из корзины без восстановления (UC-33).
