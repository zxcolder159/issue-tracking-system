# Project Vision — Issue Tracking System

## Что мы строим

Веб-система управления задачами в духе Jira / YouTrack / Kaiten: несколько изолированных пространств (проектов), в каждом — свои участники, роли и настраиваемый процесс. Мы хотим построить не «список задач с полями», а инструмент, в котором команда сначала описывает свой рабочий процесс, а затем система помогает ему следовать.

## Ключевая идея: процесс важнее задач

Главной сущностью системы мы видим не issue, а **lifecycle** — граф статусов и разрешённых переходов. Board — это материализация графа: каждый столбец — статус, а перетаскивание карточки — не «изменение поля», а переход по ребру графа, который система либо разрешает по правилам, либо внятно отклоняет. Поэтому настройка столбцов (создание, порядок, правила переходов) для нас не второстепенная фича, а ядро продукта.

## Принципы

1. **Пространство — отдельный мир.** Свой набор пользователей и ролей; один человек может быть Project Lead в одном проекте и Developer в другом. Права проверяются в контексте пространства, а не глобально.
2. **Права понятны и предсказуемы.** Developer редактирует только свои issues, Project Lead — любые. Любой запрет должен быть объясним: пользователь всегда понимает, почему действие недоступно, а не упирается в молчаливую ошибку.
3. **Данные не теряются молча.** Удаление — всегда soft delete с корзиной на 7 дней и возможностью восстановления. Принцип: лучше лишняя корзина, чем потерянная задача.
4. **Минимум трения.** Board view — основной режим работы: карточка, drag-n-drop, date picker для дат, всё важное видно без открытия карточки. List view — для обзора всего бэклога и массовых операций.

## Критерии успеха Stage 1

Команда из нескольких человек может: создать пространство, добавить участников с ролями, настроить собственные статусы и правила переходов, завести бэклог и вести его на доске. При этом система корректно запрещает неразрешённые переходы и правки вне полномочий роли, а удалённая задача восстановима из корзины. Всё это — стабильно, без ручных костылей в данных.

## Не-цели Stage 1

Комментарии, история изменений, уведомления, дашборды и интеграции осознанно откладываем (часть из них уточняем у заказчика), чтобы Stage 1 получился законченным и надёжным, а не набором полуготовых функций.

## Куда развиваем

Комментарии и история изменений issue → поиск и фильтры → метрики по пространству (узкие места lifecycle, просрочки) → API и интеграции. Lifecycle как граф даёт задел на будущее: на нём естественно строятся отчёты, SLA-правила и автоматизации.
